## 二、为什么需要可以交互的回答？

AI 可以把回答呈现为图表、卡片，以及可以操作的小工具。

很多时候，用户拿到一个答案之后，还需要继续调整条件、比较选项，或者完成某个操作。单靠文字，整个过程可能会变得很繁琐。

比如，我准备在周日邀请朋友来吃烤羊腿。AI 可以帮我生成采购清单、准备步骤和烹饪时间表。

但是，如果用餐人数发生变化，我就需要重新提问，再从新的长回复里寻找变化的部分。

## 三、什么是 A2UI？

![什么是 A2UI](images/07-s-a2ui-intro.png)

A2UI 是实现这类界面体验的一种方式。

应用先在客户端准备好一套组件，例如文字、图片、按钮和输入框。Agent 通过结构化消息，描述需要使用哪些组件、如何排列，以及显示什么内容。

客户端收到这些描述之后，再把它们渲染成用户可以操作的界面。

这里，Agent 提供的是界面描述，最终的显示和交互由客户端完成。

## 四、Agent 怎样描述一个界面？

我们来看一个简单的例子。

用户说：“帮四个人订一张桌子。”

画面中的 JSON，就是这个预订界面描述的一部分。

![组件、布局、内容、数据绑定和操作](images/08-s-a2ui-code.png)

首先，Agent 选择需要使用的组件。然后，通过组件 ID 定义它们之间的排列关系，并填入标题、按钮文字等内容。

一些组件还可以连接到数据，例如这里的用餐人数。

按钮则可以指定操作，让应用知道用户希望执行什么，以及需要提交哪些参数。

这些部分组合起来，就形成了一个用户可以继续交互的界面。

### 从描述到界面

## 五、用制作奶茶理解 A2UI

### 组件：提前准备好的材料

![奶茶材料与预定义组件](images/10-s-bubble-tea.png)

我们可以把这个过程想象成制作一杯奶茶。

茶、牛奶、珍珠和杯子，就像提前准备好的 UI 组件。每一种材料都有自己的用途，以及相应的使用规则。

### JSON：组合材料的配方

![Agent 生成组合配方](images/11-s-bubble-tea-recipe.png)

Agent 根据用户的需求，决定选择哪些材料、使用多少，以及怎样组合。

Agent 生成的 JSON，就像制作这杯奶茶的配方。

对于用户界面来说，这份配方描述的是：使用哪些组件、把它们放在哪里，以及连接哪些数据。

### 客户端：按照配方呈现成品

![客户端组合出最终结果](images/12-s-bubble-tea-make.png)

客户端按照配方，把这些部分组合起来，最终呈现出用户看到的结果。

也就是说，应用提供组件，Agent 描述组合方式，客户端完成渲染和交互。

## 六、连接 ADK、AG-UI 和 A2UI

![餐厅 Agent 的整体架构和交互回路](images/13-s-restaurant-architecture.png)

现在，把这个过程放进我们的餐厅场景。我们需要连接三个主要部分。

### ADK：组织 Agent 的执行

左边是 Agent 后端。

我们使用 Google 的 Agent Development Kit，也就是 ADK，组织 Agent 的执行，并让它调用业务工具，例如查询菜单和检查预订桌位。

### AG-UI：连接后端与前端

中间是 AG-UI。

它负责 Agent 与前端之间的通信，传递消息、工具事件和状态更新。我们也可以通过这条通信链路，把 A2UI 的界面描述送到前端。

### 客户端：渲染和处理交互

右边是客户端。

客户端收到界面描述后，通过 A2UI 渲染器和组件目录，显示实际的用户界面。

当用户选择时间并点击预订按钮时，应用会把操作和参数传回后端。后端检查实际桌位，执行对应的业务操作，再返回确认结果和必要的界面更新。

这样，我们就形成了一个完整的交互循环。

### 三者的分工

![ADK、AG-UI 与 A2UI 分工总结](images/14-s-restaurant-summary.png)

简单记住三句话：

ADK 负责运行 Agent。

AG-UI 连接 Agent 和用户界面。

A2UI 描述需要渲染的界面。

## 九、明确餐厅 Agent 的功能

![从需求开始规划](images/21-s-plan-mode.png)

开发环境准备好之后，先想一想：我们希望这个 Agent 帮助用户完成什么？

从一次餐厅点餐体验出发，可以把需求分为四个部分。

![Explore、Recommend、Explain、Order 四个功能](images/22-s-agent-features.png)

第一，Explore，浏览菜单。用户应该能够查看菜品图片、价格和供应情况。

第二，Recommend，推荐菜品。Agent 应该根据用餐人数、预算和饮食偏好，帮助用户进行选择。

第三，Explain，解释菜品。用户可以询问食材、热量，以及已标注的过敏原信息。

第四，Order，检查和提交订单。用户应该能够检查已选菜品、修改数量、确认总金额，并明确提交订单。

这四个功能，组成了我们的餐厅应用。

## 十、开发前还需要明确什么？

![数据库、模型、技术栈和体验设计](images/23-s-agent-note.png)

有了功能之后，还需要考虑怎样把它们变成一个可以工作的应用。

首先是菜单数据库。价格、图片、介绍和供应状态，都需要来自数据源。这个演示可以使用模拟数据，但 Agent 的回答仍然应该依据这些记录。

接下来是模型选择。我们需要结合响应速度、表现和成本，选择适合的模型。

然后是技术栈，以及各个部分之间的连接方式。

最后，还要考虑用户体验。哪些信息适合通过文字解释？哪些任务更适合用交互界面完成？

例如，推荐理由和食材说明可以放在对话中，而筛选条件、修改数量和检查订单，则适合让用户直接操作。
